사용자 원문: "배터리나 발열같은거 최대한 안먹을 수 있도록 최적화에 최대한의 힘을 쓸 것".

## 1. 왜 발열이 나는가 (iPad·노트북)

1. **GPU 점유율 × 지속 시간이 열이다.** 팬 없는 iPad·MacBook Air는 SoC가 3–5W를 넘는 부하를 10–20분 이어 가면 외장이 따뜻해지고, 그다음 클럭을 내려(스로틀) 같은 그림에 더 긴 프레임이 걸린다. 그러면 점유율이 오히려 올라가는 악순환이 생긴다. 집중 타이머(25–90분, 화면 켜 둠)가 바로 그 '지속' 상황이다.
2. **고주사율은 모든 비용을 곱한다.** 120Hz에서는 프레임마다 GPU 그리기, 합성기, backdrop 블러, 디스플레이 파이프라인이 두 배로 돈다. ProMotion 패널은 화면이 정지하면 10–24Hz까지 내려가 패널 전력을 아끼는데, **매 vsync마다 rAF를 거는 것만으로도 120Hz에 묶인다**(그리지 않고 건너뛰어도 마찬가지).
3. **깨우기도 비용이다.** 초당 120번 깨어나면 CPU가 깊은 유휴 상태(C-state)에 들어가지 못한다. 30fps 상한이면 깨우기도 30/s여야 한다.
4. **해상도는 채우기 비용에 바로 들어간다.** iPad 11" = 2388×1668(4.0MP). 축마다 ×0.75면 면적이 0.56배로 줄어 채우기가 44% 준다. 하늘(점·성운·블룸)은 부드러운 그림이라 0.6–0.75배 업샘플이 눈에 거의 띄지 않는다.
5. **iPad Safari에는 Battery API와 GPU 타이머 쿼리가 없다.** 저전력 모드에서 Safari는 rAF를 30Hz로 묶는다. 그래서 iPad의 저전력·발열 감지는 '프레임 간격'으로 해야 한다(§4-6).

## 3. 집중 타이머 화면: 왜 '쉼'으로 빨리 들어가야 하나

- **시간이 길다.** 25·50·90분 동안 화면을 켜 두고 손을 떼고 있다. 이 상태의 비용이 앱 하루 에너지의 대부분이다.
- **계산(같은 그림 기준, 해상도 배율은 면적으로):** 지금은 120fps × 3.1–4.3ms → 373–520ms/초다.
  - §7-4 그대로: 처음 60초 30fps×0.75(≈ 52–73ms/초), 이후 4분 15fps×0.6(≈ 17–23ms/초), 5분 뒤 쉼.
  - 제안안: 20초 뒤 쉼. 쉼에서는 별 자람 1장/초(≈ 4ms/초).
  - 50분 세션의 GPU 시간: 지금 ≈ **19–26분**, §7-4 ≈ 0.3분, 제안안 ≈ 0.2분. 두 안 모두 지금보다 99% 적다.
- **차이는 '손을 댈 때마다'에서 난다.** 집중 중에도 사람은 화면을 건드린다(일시정지, 남은 시간 확인, 실수 터치).
  - §7-4: 터치 한 번에 5분 동안 움직이는 하늘이 다시 돈다. GPU ≈ 8.4초, 깨우기 ≈ 5,700번, 그동안 패널은 고주사율에 묶인다.
  - 제안안: 같은 터치에 20초. GPU ≈ 1.2초, 깨우기 ≈ 620번.
  - 하늘이 정지하면 ProMotion이 저주사율로 내려간다(숫자는 1초에 한 번만 바뀜). 패널 전력은 GPU보다 크다.
- **보는 사람:** 집중 중 시선은 과제에 있다. '은하가 숨을 고르고 잠든다'는 연출로도 맞는다(2초 크로스페이드, 밝기·구도 그대로).
- **살아 있는 느낌은 별이 맡는다.** 자라는 별(growStar)이 1초마다 한 장씩 다시 그려진다. 25분이면 1초에 0.07%라 사실상 정지해 보인다. 5초에 한 장으로 줄여도 같아 보인다(모션 개발자 판단).
- **아트 디렉터가 움직임을 원할 때의 대안:** 입력 10초 뒤 깊은 대기(15fps ×0.6, 공전 0.3°/s)를 2분 이어 간 다음 쉼으로 간다. 50분 GPU ≈ 0.25분, 터치당 2분 10초(깨우기 ≈ 2,200번).
- 숫자는 MM:SS라 1Hz 갱신이 본질이다. 더 줄이려면 '저전력이면 분만 표시'를 디자이너에게 옵션으로 묻는다(이번에는 바꾸지 않음).

## 4. 모션 개발자에게 (galaxy3d → src/fx 통합 때 구현할 전력 모드)

1. **프레임 스케줄러(가장 먼저).** 지금 `frame()`은 매번 `requestAnimationFrame(frame)`을 다시 걸고 `FRAME_MS`보다 이르면 return한다 → 30/15/0fps에서도 깨우기 120/s, 패널 120Hz 고정(측정: 시제품 그린 fps 0 · rAF 120/s).
   - 상태 fps < 기기 주사율이면 `setTimeout(() => requestAnimationFrame(frame), max(0, due − now − 4))`로 다음 프레임 직전에만 깨운다.
   - 쉼·숨김·동작 줄이기에서는 아무것도 예약하지 않는다. `kick()`은 입력(pointerdown·wheel·key), 사건 API 호출, resize, visibilitychange에서만 부른다.
   - 2.5D 하늘(`src/galaxy/sky/sky.ts`)의 B·C 등급 `cap`도 같은 방식이다. 3D로 바꾸기 전에 **2.5D 하늘에도 §2 상태(평소 30·깊은 대기 15·집중 쉼)를 먼저 넣으면** 지금 앱의 GPU 시간이 70–95% 준다. 효과가 가장 큰 단일 작업이다.
2. **가변 fps 값:** 활동 60(비행·드래그) / 평소 30 / 깊은 대기 15 / 쉼 0. 전환은 히스테리시스를 둔다(올릴 때 즉시, 내릴 때 2초 `inout`). 시간 기반 상태(공전각·자전 `simT`·호흡)는 항상 `performance.now()`에서 계산하므로, 프레임을 건너뛰어도 보간이 필요 없다.
   - 15fps에서 공전 0.3°/s = 프레임당 0.02°이고, 전경 별 ≤ 24px/s = 프레임당 1.6px이다.
   - 깊은 대기에서는 전경 별 속도도 ≤ 10px/s로 묶는다(프레임당 0.7px, 끊김 없음).
3. **동적 해상도:** 장면 RT 배율 1.0 / 0.75 / 0.6. 총 픽셀 상한 4.0MP(iPad 11" DPR 2 = 4.0MP, 13" = 5.6MP → ×0.85).
   - 배율은 **카메라가 움직이는 순간이나 상태 전환 크로스페이드 안에서만** 바꾼다(정지 화면에서 갑자기 선명도가 바뀌지 않게).
   - 블룸은 평소 5단, 깊은 대기 4단, 쉼은 마지막 1회. ½·¼ 해상도 버퍼(먼지·성운)는 배율을 그대로 따른다.
4. **정적 층 캐싱:**
   - (a) 먼 하늘(헤일로·구상성단·먼 은하·하늘 구 별)은 카메라 거리와 무관하다. 방위·고도가 2° 넘게 바뀔 때만 ½ 해상도 텍스처로 다시 굽고, 그사이에는 1탭 전체 화면 패스로 그린다.
   - (b) 쉼에 들어갈 때는 합성 전 HDR 장면을 한 장 굽는다. 그 뒤 사건(별 자람·탄생·선)은 그 위에 **데이터 별 패스만 덧그린다**(40만 점을 다시 그리지 않음).
   - (c) 집중 쉼에서 자라는 별은 작은 시저 영역(별 주위 64px)만 다시 그린다.
5. **프레임 생략 시 보간:** 위치는 시간에서 직접 계산하므로 보간이 필요 없다. 필요한 곳은 둘이다.
   - (i) 상태가 내려갈 때 전경 별 모션 블러 꼬리를 프레임 간격에 맞춰 늘린다(≤ 24px 유지).
   - (ii) 돌아올 때 600ms 램프는 **속도**를 0→목표로 올린다. 위치를 점프시키지 않는다.
   - 입력 첫 프레임은 다음 vsync에 바로 그린다(쉼에서 깨어날 때 setTimeout을 기다리지 않음).
6. **저전력·발열 감지(iPad 포함):**
   - Chrome: `navigator.getBattery()`(level ≤ 0.2 && !charging, `levelchange`·`chargingchange` 구독), `navigator.connection.saveData`.
   - **iPad Safari: 두 API가 없다.** 활동 중 rAF 간격 중앙값이 2초 동안 30–34ms이면 저전력 모드로 본다(120·60Hz 기기에서 Safari가 30Hz로 묶음).
   - 발열: 프레임 p95 > 예산 × 1.5가 10초 → 한 단계 내림. Chrome에서는 타이머 쿼리 GPU ms/초 > 400이 30초여도 한 단계 내린다.
   - `prefers-reduced-motion`은 정지 장면이다. 감지 결과는 `__g3d.stats().power`와 `getSkyStats().power`로 내보내면 `__gyeolPower`가 함께 기록한다.
7. **숨김:** `visibilitychange`·`pagehide`에서 rAF를 취소하고 타이머를 0으로 한다. 지금 2.5D 하늘은 `document.hidden`이면 루프를 멈춘다(좋음). 3D 시제품에도 같은 처리가 필요하다(지금은 `frame()`이 계속 다시 걸림).
8. **Worker 입자 생성:** 시작 긴 작업 360ms → 0. 앱 첫 진입의 CPU 피크가 사라진다(발열보다 첫 반응 문제).
9. **fx 쪽 작은 것들 (이번에 앱에서 우회만 함):**
   - `ProgressLine`(`src/fx/fx.css` 224·226행): `transition: left 1s linear`이 매초 다시 걸린다 → 집중 내내 **메인 스레드 배치 애니메이션**이 끝없이 돈다(측정: 표본 7/7초). 앱 CSS로 집중 실행 중에만 끄도록 덮어 두었다.
   - 근본 수정: 표시 막대를 `transform: translateX`로 바꾸고, 값 변화가 1px 미만이면 전환을 생략한다.

## 6. 측정 방법과 합격 기준

**도구(개발 빌드에만 있음):**
- 앱 콘솔: `await __gyeolPower.measure(10)` → 그린 fps, rAF·타이머 깨우기/초(등록한 곳별), rAF JS ms, GPU ms(평균·p95·초당), React 커밋(공간별, 숨은 커밋 수), 메인 스레드·합성 애니메이션이 돈 초, 긴 작업, 네트워크 요청, JS 힙.
- `__gyeolPower.snapshot()` → 지금 도는 애니메이션, 보이는 backdrop-filter 면적, 전력 힌트(DPR·saveData·동작 줄이기).
- 3D 시제품 콘솔: `(await import('/src/perf/power.ts')).install()` 뒤 같은 명령.

**절차:**
1. 탭을 앞에 띄운다(미리보기 창이 가려지면 Chrome이 프레임을 멈춰 0이 찍힌다).
2. 3초 손 뗀다.
3. 측정 10초를 상태마다 2회 한다.

- 집중은 시작하고 30초 뒤에 잰다.
- 숨김은 다른 탭으로 옮긴 뒤 `setTimeout`으로 예약해 잰다.

**합격(모든 상태):**
- §2 표의 fps·GPU ms/초·깨우기 이하일 것.
- 정지 상태의 React 커밋 0, 메인 스레드 애니메이션 0초, 네트워크 0, 콘솔 오류 0일 것.
